# allure-labels-gate

Шаг CI, который роняет сборку, если в результатах Allure есть автотест без обязательных
лейблов. Тесты, в имени которых есть `allure` (в любом регистре, в том числе внутри слова),
не проверяются.

Скрипт один, в двух вариантах с одинаковым поведением — берите тот, что удобнее на вашем агенте:

| файл | что нужно на агенте |
|---|---|
| `check_allure_labels.py` | Python 3.8+ |
| `check_allure_labels.sh` | bash 3.2+ и jq 1.6+ |

## Настройка

Две настройки. Их можно поменять в начале скрипта или задать переменными окружения
с теми же именами; переменная окружения важнее. Пустая переменная считается незаданной.

| переменная | что задать | по умолчанию |
|---|---|---|
| `ALLURE_RESULTS_DIR` | папка результатов Allure этого проекта | не задана — **обязательно** |
| `REQUIRED_LABELS` | имена лейблов через запятую | `epic,feature,owner` |

Путь у каждого проекта свой, поэтому умолчания нет. Где искать папку:

| проект | обычно |
|---|---|
| Maven + allure-junit5 | `target/allure-results` (задаётся `allure.results.directory` в `allure.properties`) |
| Gradle с плагином Allure | `build/allure-results` |
| Jest, Playwright | `allure-results` или `resultsDir` в настройке адаптера |
| pytest | то, что передано в `--alluredir` |

## Подключение

Шаг ставится **после** тестов и должен выполняться, даже если тесты упали.

```bash
ALLURE_RESULTS_DIR=target/allure-results python3 check_allure_labels.py
# или
ALLURE_RESULTS_DIR=target/allure-results bash check_allure_labels.sh
```

В многомодульном проекте у каждого модуля своя папка результатов — запускайте скрипт
на каждую. Папку результатов чистите перед прогоном тестов: старые файлы тоже попадут в проверку.

## Коды выхода

| код | что значит | что делать |
|---|---|---|
| `0` | у всех проверенных тестов лейблы на месте | — |
| `1` | есть тесты без лейблов, они перечислены | поставить лейблы в тестах |
| `2` | проверить не получилось: путь не задан или не найден, в папке нет результатов, файл не читается, нет jq | поправить настройку шага |

Код `2` тоже роняет сборку: пустая папка или неверный путь не должны выглядеть как «всё хорошо».

## Что печатает

Настоящий вывод, середина сокращена:

```
Allure results: target/allure-results
Required labels: epic, feature, owner
Tests found: 9, not checked because the name contains "allure": 1

Tests missing required labels:

  com.example.billing.LabelsContractTest.allureInMethodNameOnly
    name:    display name without the word
    missing: feature, owner

  com.example.billing.LabelsContractTest.disabled
    name:    disabled()
    missing: feature, owner

  …

FAILED: 7 of 8 checked tests are missing required labels.
```

Первая строка теста — полное имя (класс и метод, в JS — файл и `describe`), по нему тест
находится в коде. `name` — имя, которое видно в отчёте Allure.

## Что считается

- Тест — файл `*-result.json` в папке результатов. Остальные файлы (контейнеры,
  вложения, `executor.json` и прочие) не читаются.
- Лейбл есть, если у него непустое значение. `@Feature("")` и значение из одних пробелов —
  лейбла нет.
- Перезапуск упавшего теста пишет ещё один файл; в отчёте такой тест один. Вызовы
  параметризованного теста — разные тесты.
- Пропущенные тесты (`@Disabled`, `it.skip`) тоже проверяются. В JS лейблы ставятся
  внутри тела теста, поэтому у пропущенного JS-теста их нет.
- Слово `allure` ищется в имени теста из отчёта. В JUnit 5 это `@DisplayName`, если он
  задан, иначе имя метода. Имя класса и пакета не учитывается.

Подробно, со ссылками на настоящие прогоны, — [`docs/contract.md`](docs/contract.md).

## Проверка самого скрипта

```bash
tests/run.sh        # оба варианта на всех случаях из tests/cases
tests/real-run.sh   # свежий прогон настоящего Java-сервиса и JS-проекта с Allure
```
